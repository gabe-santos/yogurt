# Feed Icons are stored as downscaled blobs, not hotlinked

Every Entry row carries a Feed Icon beside the publisher's name. The icon is discovered by parsing `<link rel="icon">` from the Feed's `site_url` — conventional path probing was measured and rejected, since bare `/favicon.ico` 404s on two of the first three subscribed sites. The chosen file is fetched, downscaled to 32px when it is a raster larger than that, and stored as a BLOB on the Feed row; SVG and ICO are stored untouched, because there is no pure-Go SVG rasteriser and no stdlib ICO decoder, and browsers render both natively.

**Hotlinking the publisher's icon URL** was the cheaper option and was rejected on two grounds. It leaks reading behaviour: the entry list would tell every publisher that this reader saw their headline, for every Entry, including the ones never opened — a worse exposure than Article images, which at least imply the Article was requested. It is also wasteful in practice rather than in theory: one of the three sites serves a 170x170, 58,377-byte PNG as its only icon, shipped in full to paint sixteen pixels, where a stored 32px copy is roughly 1 KB. **Files in a new asset directory** were rejected in favour of a BLOB so that the data directory stays a single `reader.db`, preserving the property that a backup is one file, and so that icons are evicted by the existing Feed foreign key rather than a new cleanup path.

Discovery runs at subscribe time and opportunistically during refresh when an icon is missing or older than thirty days, which makes backfill of existing Feeds free and needs no new worker. A single `icon_checked_at` gates both success and failure, so a site with no usable icon is re-probed once a month rather than on every poll. Icon bodies are capped far below the default fetch limit, and icon URLs go through the ordinary fetch client so the private-network guard still applies — this matters more here than for Feed URLs, because these paths are publisher-controlled rather than user-entered.

Consequence: this narrows the MVP PRD's exclusion of an image proxy, which was written against proxying Article body images, not against a bounded set of one small icon per Feed. The per-Entry Preview Image, sourced from an Article's OpenGraph metadata, is a separate and unbounded case; it is deliberately not decided here.

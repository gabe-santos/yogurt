# Go + SQLite serving an embedded SvelteKit SPA, as one binary

One process, one file, one container: a Go binary running an HTTP API and a feed-pull worker over SQLite (`modernc.org/sqlite`, pure Go, no cgo), with the compiled frontend embedded via `embed.FS`. Feed parsing uses `gofeed`, discovery `feedfinder`, extraction `go-readability`. The design deliberately tracks fusion (`github.com/0x2E/fusion`), whose backend serves as a reference implementation for the pull scheduler, fetch-state schema, FTS5 triggers and SSRF guards. Rust and Bun were the credible alternatives — Rust for footprint, Bun for one language end to end — and lost because the whole relevant library ecosystem (`gofeed`, `feedfinder`, `go-readability`, `obelisk`) plus the reference implementation are Go.

The frontend is **Svelte** (SvelteKit with `adapter-static`, `fallback: 'index.html'`, `ssr = false`), shadcn-svelte on Tailwind v4, `@tanstack/svelte-query` for caching and optimistic updates. This deviates from fusion, which is React, and from the more conservative choice: shadcn/ui is the canonical shadcn, and React has the deeper answer pool. Svelte was chosen because the author wants to learn it, the frontend is the cheapest layer in this system to replace, and the fusion behaviour worth copying lives in the Go backend, not the UI. Scoped CSS with explicit `:global()` also suits styling sanitised publisher HTML, which is this app's central rendering job.

SvelteKit runs strictly as a static SPA. No `+page.server.ts`, no form actions, no server-side environment access: the moment the frontend has a server, the project has two backends and the single-binary deployment story is gone. TanStack Start was rejected for the same reason — its value is server-side, and disabling that leaves only ceremony.

# Selection is opening

With a permanently populated Reading Pane, selecting an Entry and opening it are one gesture, so Read is set the moment an Entry reaches the Reading Pane, and the `mark_on_open` setting (internal/api/settings.go) now gates exactly that. A dwell timer was considered, so that skimming with j would not consume the list; it was rejected because an invisible timer is unexplainable to the reader and untestable in a way anyone believes. The cost is that fast keyboard skimming marks Entries Read in passing; Mark-unread is the undo, and the manuallyUnread guard keeps a hand-unread Entry from being re-marked.

One consequence is worth naming, because it looks like a bug: an Entry being read stays in the Entry List even once it is Read and Unread Only no longer takes it in. It used to leave as soon as the reader moved off it; 0014 removed that step too, so nothing takes an Entry out of the Entry List but the reader rebuilding it. Letting the automatic Read remove it would have taken the arrival that replaced it as well, and the one after that, until the list had emptied itself.

Position, however, outlives the selection. Before there is room for a third column the Reading Pane is an overlay, and backing out of it clears the selection — which took the reader's place in the list with it, so `j` started the list again from the top and the overlay's focus was dropped on the document body. The row a closed Entry was on is therefore remembered separately (`closedIndex` in web/src/routes/+page.svelte), and `position` is whichever of the two the reader is actually at: what `j` and `k` count from, the Entry List's single tab stop, and the row that takes focus back when the overlay closes. Only rebuilding the list forgets it. Selecting is still opening; closing is simply not moving.

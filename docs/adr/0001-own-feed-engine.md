# Own feed engine rather than a client on Miniflux or FreshRSS

Polling, conditional GET, backoff and dedup are already solved by Miniflux and FreshRSS, so building on one of them as the feed engine was the obvious alternative. We rejected it because neither exposes an API that can *create* an entry — both are read/sync-shaped — and the planned newsletter feature turns inbound email into entries. Riding an existing engine would mean generating a local feed for it to poll back out of us, and operating two services with a foreign data model. We run our own engine instead, and copy fusion's proven pull design (per-feed `etag`/`last_modified`, `next_check_at`, `Cache-Control` honouring, `interval * 1.8^failures` backoff capped at 48h, SSRF guards on feed fetches) rather than inventing one.

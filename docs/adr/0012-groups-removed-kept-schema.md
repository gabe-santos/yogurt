# Groups are removed from the reader, the table and column stay

Groups let a Feed belong to a named, non-nesting set for scoping (PRD stories 21-23, 26, 41-42). With one reader and a handful of subscriptions, that structure was overhead the product never needed: manage mode, the Group context menu, a New Group form, move/rename/delete plumbing duplicated per-Group, and OPML folders that had to be flattened into Groups on import and reconstructed on export. We removed all of it in two steps (#28 flattened the Feed List to `All Feeds` plus every Feed, sorted by title, and deleted manage mode and Group scoping from the client; #30 removed the `/groups` endpoints, the group store, and the Group id from the Feed representation and patch, and collapsed subscribing to one path). OPML import now ignores folders and subscribes every Feed it finds; export writes one flat list.

The `groups` table and `feeds.group_id` column stay in the schema, unreferenced by any remaining code path. Every Feed still carries a `group_id`, defaulted to the seeded `Unsorted` Group's id, but nothing reads it to scope, display, or filter anything anymore. We chose keeping over a migration that would drop the table and column: with them in place, re-adding Grouping later is purely additive — no column has to be re-created and backfilled, and no existing Feed's data is disturbed — against a migration now and a second migration to bring the table and column back if Grouping returns. The cost is a table and a column doing nothing for as long as Grouping stays out; that is worth paying once rather than migrating twice.

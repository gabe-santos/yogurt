# The menu material is always dark

The dropdown menus, context menus and Select lists are dark whatever colour scheme the OS asks for. In a light scheme they are the one dark surface in the product; in a dark scheme they are what they always were. This is shadcn's `menuColor: inverted-translucent`, recorded in `web/components.json`, and the generator materialises the colour half of it as a single literal `dark` class on each menu content element — that class substituted for a `cn-menu-target` marker is the whole of the upstream mechanism, with no custom properties, no data attributes and no generated CSS. The five content elements carry that class by hand rather than by regeneration, because `shadcn-svelte update` would have restored every animation utility that the polish pass in `6b35500` deliberately stripped from these same class strings.

A `dark` class only means something if something defines it, and half of that plumbing was removed on purpose: `7a1808a` deleted `@custom-variant dark (&:is(.dark *))` and the `.dark` token block that `init` had written, so `dark:` in this project is Tailwind's default `prefers-color-scheme` query and there is no theme toggle. Rather than reverse that, `app.css` now defines a global `.dark` block that carries the token set and nothing else — the variant definition is untouched, so `dark:` utilities still follow the OS everywhere including inside an inverted menu. The dark palette's literals were hoisted into `--dark-*` variables that both the ambient scheme and this scope read, because two hand-maintained copies of thirty-three tokens drift. `color-scheme: dark` rides along so a scrolling Select draws a dark scrollbar down a dark sheet.

The alternative shapes were a token override keyed on `data-slot`, which invents a mechanism upstream does not use and gains nothing over the class it would replace, and a dual-mode `dark` variant matching both `.dark` descendants and the media query, which would have made `dark:ring-foreground/10` fire inside a light-mode menu for free at the price of two ways to be dark and a duplicate of every `dark:` rule in the compiled CSS. Inverting *relative to* the ambient scheme — the reading of "inverted" that would make menus light at night — was rejected and is not what the generator does either: its transformer has no light counterpart to the `dark` substitution.

Three consequences follow. The hairline ring is forced to its dark-tuned 10% on these surfaces, since the 5% value is now permanently wrong and the `dark:` gate that would have corrected it can never open in a light scheme. The Tooltip keeps its own rule: `bg-foreground text-background` makes it inverted relative to the scheme, so it is light at night while the menus stay dark, which is a label maximising contrast against what it covers rather than a sheet you read down. And the inversion extends one component past upstream: the registry marks `dropdown-menu`, `context-menu`, `select` and `menubar`, but not `popover` — so `popover-content` is pre-wired into the material rules here, and a Popover or a Combobox (which is a Popover holding a Command list; there is no `combobox` registry item) needs the `dark` class added by hand at install time. Sidebar is deliberately outside all of this: upstream does not mark it either, and a permanently dark rail is a change to the three-pane layout that 0009 settled, not a change to a transient overlay.

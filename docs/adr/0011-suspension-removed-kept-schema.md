# Suspension is removed from the reader, the column and index stay

A Feed could be suspended to quiet a noisy publisher without losing its history (PRD story 20). In practice it added a second way to stop seeing a Feed's Entries — alongside deleting it — for a benefit that never earned its keep: a single reader with a handful of subscriptions can just delete and re-subscribe, and re-subscribing starts the Feed from scratch anyway, so suspension's only real advantage over deletion (keeping history) was rarely, if ever, the reason to reach for it. We removed it (#26): no Suspend/Resume affordance in the UI, no `suspended` field on the Feed API or patch, no skipping of suspended Feeds in the pull schedule — every Feed is checked.

`feeds.suspended` and the partial index `feeds_due ON feeds (next_check_at) WHERE suspended = 0` stay in the schema, unreferenced by anything that writes to them again. Nothing ever sets the column to 1 now, but `DueFeeds` keeps the `suspended = 0` predicate in its query — an always-true condition given the column is permanently 0 — purely so the query still matches the partial index's `WHERE` clause; dropping the predicate would make SQLite fall back to a full scan of `feeds`. Dropping the column and index outright would need a migration and would foreclose resurrecting suspension later without one. Keeping both costs one always-true predicate and a comment explaining it (`internal/store/feeds.go`), against the option of a migration now and another to bring it back.
